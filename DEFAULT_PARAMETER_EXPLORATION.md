## OrthoFinder Comparator Provenance

An audit on 2026-07-15 found that every cached OrthoFinder benchmark log
reports version 2.5.5. The old container was named `orthofinder_latest.sif`,
but `orthofinder --version` inside it reports 2.5.5. Therefore, all numeric
OrthoFinder scores below are historical 2.5.5 results and cannot be presented
as OrthoFinder 3 results.

The current benchmark setup is pinned to OrthoFinder 3.1.5 through
`benchmark_tools/orthofinder.sh`. The exact upstream release archive is
verified against SHA-256
`d74b5dbf9348e7ffdb735f1fda4ff9c49f504261811355519cf9dafcf80e7739`,
and each runner fails if the executable does not report
`OrthoFinder:v3.1.5`. New output labels include `orthofinder_v3_` so they do
not overwrite or silently reuse the legacy result directories.

OrthoFinder 3.1.5 moves the root HOGs formerly written as `N0.tsv` into
`Orthogroups/Orthogroups.tsv`; its corresponding text representation is
`Orthogroups/Orthogroups.txt`. The updated runners collect that root-HOG text
file. The QfO runner now converts OrthoFinder's native phylogenetic orthologue
tables instead of treating every root HOG as a complete orthology clique.

Fresh OrthoBench runs completed on 2026-07-15. OrthoFinder 3.1.5 DIAMOND
scores F=72.7, precision=66.1, and recall=80.9; MMseqs scores F=63.5,
precision=52.1, and recall=81.5. The DIAMOND result overturns the previous
conclusion based on v2.5.5: the current OrthoHMM candidate no longer leads
OrthoFinder on OrthoBench F-score, although OrthoHMM remains much more precise.

The v3 QfO DIAMOND inference completed in 22h29m and produced 13,441,634
native pairs. Its first assessment attempt exposed benchmark-ineligible IDs
that occur in the official proteome FASTAs but are absent from the QfO 2020
mapping. A mapping-based filter retains 2,371,225 scoreable pairs while
preserving the raw pair file; the filtered file passes the official validator.
The corrected DIAMOND assessment reached all six metric tasks, but FAS exceeded
the retry job's 20 GB memory allocation; its completed Nextflow work can be
reused with `RESUME=1` and at least 100 GB. QfO MMseqs completed its
18,862-sequence, 2.0 GB FastTree input after roughly four days, then OrthoFinder
3.1.5 stalled at 20,153/20,154 orthogroups during orthologue inference. It
therefore produced no complete native pair set and has no valid QfO score.

## Current Best Candidate

The strongest candidate is the default refinement change that adds a
medium-panel copy-number split for large clusters in datasets with at least
10 species. The behavior is implemented in `orthohmm/refinement.py` and is
covered by the medium-panel refinement tests in `tests/unit/test_refinement.py`.
For QfO-scale inputs, the broad copy-number split default is aligned with the
cached `split_s150_c10` evidence: minimum cluster size 150 and minimum
dominant-species copy count 10.

The best experimental OrthoBench evidence is the fresh cached downstream replay
from `orthogroups_ablation_A_full_v2.txt` with RBNH edge weights passed into
refinement: F=70.4, precision=79.1, recall=63.4, and 13 exact RefOGs. This is
the strongest reproducible current-code replay found so far, but it is an
accuracy candidate rather than a verified production default.

A fresh production CLI run completed on 2026-08-27. It scored F=63.8,
precision=85.2, recall=51.0, with 12 exact RefOGs. The run scored 45,440,595
candidates and retained 9,743,225 significant hits. This confirms that the
70.4 replay base is not generated by the current production pipeline: it came
from the experimental multi-pass workflow and fixed-`mc100` search, which
scored about 298 million candidates. The cached replay remains valid evidence
for that algorithm, but it must not be presented as an end-to-end production
result.

The optimized production implementation was rerun end to end on the same
input. It reduced wall time from 2,145.66 to 978.63 seconds and reproduced the
baseline edge list, pre-singleton clusters, and final orthogroups byte for
byte. Its official OrthoBench score is therefore unchanged; the performance
work does not close or worsen the separate production accuracy gap.

### Cached Downstream Replays

To verify that the current refinement code path can reproduce an
OrthoBench-beating result without hand-editing predictions, I replayed the
refinement stage from cached downstream artifacts. The current production
refinement wiring passes RBNH edge weights into `refine_cluster_indices`, which
lets the medium-panel split preserve strong within-cluster components instead
of reducing every flagged cluster to singletons.

- base clusters: `benchmarks/results/orthogroups_ablation_A_full_v2.txt`
- cached hits: `benchmarks/results/hits_BLOSUM62_mc100.pkl`
- refinement entry point: `orthohmm.refinement.refine_cluster_indices`
- replay output:
  `benchmarks/results/orthogroups_default_exploration_refine_ablation_A_current.txt`

Official OrthoBench scoring for the fresh current-worktree replay output was
F=70.4, precision=79.1, recall=63.4, with 13 exact RefOGs. This supersedes the
older `orthogroups_default_exploration_refine_replay.txt` artifact, which still
scores F=68.9 and should be treated as stale replay evidence rather than the
current default-code result. The machine-readable fresh replay summary is in
`benchmarks/results/default_exploration_ablation_A_current_replay.json`.

This replay is not a substitute for a fresh end-to-end search/clustering run,
but it substantially reduces the uncertainty around whether the current
implementation can produce an OrthoBench-improving result from cached benchmark
inputs.

## Rejected OrthoBench Candidates

Cached OrthoBench sweeps over CPM, pass-3 strictness, anchor count,
cluster-merge variants, species-pair weighting, and existing pass-3
normalization variants did not beat the cached OrthoFinder 2.5.5 results. The targeted cached ranking
is in:

`benchmarks/results/default_exploration_orthobench_targeted_scores.json`

The best cached pre-refinement OrthoHMM variants plateaued near F=66.86.

A non-broad reciprocal-merge cap sweep was rejected. The hypothesis was that
suppressing reciprocal cluster merges might explain the preserved F=70.5
component-preserving replay. Direct cached replays from
`orthogroups_ablation_A_full_v2.txt` showed otherwise:

| max reciprocal merges | F-score | precision | recall | exact RefOGs |
| ---: | ---: | ---: | ---: | ---: |
| 0 | 69.4 | 79.1 | 61.9 | 13 |
| 16 | 69.4 | 79.1 | 61.9 | 13 |
| 32 | 69.4 | 79.1 | 61.9 | 13 |
| 64 | 70.4 | 79.1 | 63.4 | 13 |
| 150 | 70.4 | 79.1 | 63.4 | 13 |

Lower caps lose the recall recovered by the current default, and cap 64 only
ties the current cap 150. The sweep summary is in
`benchmarks/results/default_exploration_reciprocal_cap_replays.json`, and no
code change is recommended from this attempt.

Adaptive CPM is not a viable main default despite improving Three Kingdoms:
cached OrthoBench scoring of `benchmarks/results/orthogroups_rbnh_cpm_auto.txt`
gave F=58.6, precision=91.7, recall=43.1, and 7 exact RefOGs. The QfO
`orthohmm_cpm_auto` retained-metric mean is 0.521, below the split/refinement
candidate and both cached OrthoFinder 2.5.5 comparators. A simple species-count gate also
does not separate the secondary and primary benchmarks cleanly: OrthoBench and
Three Kingdoms both use 12 input proteomes, while QfO uses 78.

## Remaining Work

The fresh production run did not reproduce the improved cached OrthoBench
prediction. The experimental multi-pass generator must be recovered and
integrated into the production pipeline before the 70.4 candidate can become a
default. The orphaned `agg150` generation path should also be reconstructed or
discarded; it is useful evidence, but not a reproducible code path yet.
The OrthoFinder 3.1.5 DIAMOND QfO assessment should be resumed with sufficient
memory to complete FAS. The failed v3 MMseqs result should be reported as a
tool failure under its default workflow unless a reproducible upstream-safe
recovery path is identified.
