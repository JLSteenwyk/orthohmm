# Process-Inventory Policy Check

The original v1 contract below remains historical. The subsequent
[typed v2 extension](THREADRIPPER_KERNEL_IDENTITY_20260928.md) permits only
explicitly reviewed, observed-kernel display-name changes while retaining
CPU and identity checks. It does not approve an environmental policy or
complete the live preflight worker.

`benchmark_tools/review_threadripper_process_policy.py` supplies a pure,
read-only comparison for the unfinished live environmental review worker.
It does not create an approved background inventory, publish a preflight,
release a native command or change the pinned production runtime.

The existing CPU observer is diagnostic. Its 0.25-core threshold cannot
establish that no unrelated scientific work is present: an idle or sleeping
analysis still conflicts with the prospective quiet-window policy. The new
check therefore requires explicit reviewed entries for every observed outside
process, independently of its measured CPU use.

## Contract

The caller supplies two ordered process snapshots, the actual job subtree,
observer PID, boot ID and a policy with schema `threadripper_process_policy_v1`.
The policy has a matching boot ID, explicit review reference and an
`ordinary_processes` list. Each entry contains PID, creation time, cgroup,
process name, `classification: ordinary_background`, and a nonempty reason.
No wildcard, command-name-only, CPU-threshold or automatic learning exception
is supported. The observer must appear inside the job in both snapshots;
there is no arbitrary outside-observer PID exemption.

Unknown identities, disappearing approved entries, births/deaths outside the
job, changed identity/name/membership, decreased counters and observation
errors leave the inventory unresolved. Malformed values, duplicate PIDs,
invalid scopes and wrong-boot policies raise errors. A process moving into
the job between observations is not silently exempted. All inputs remain
unchanged and the original CPU diagnostic is included separately.

`reviewed_process_inventory_observed` means only that this comparison matched.
It is **not an environmental pass**: controlled-workload verification and
scientific-timing admission remain false even if all entries match. A busy
approved ordinary service remains visible in the CPU diagnostic and needs
environmental review. Callers must verify policy hashes, provenance and the
factual basis for each classification; strings and reasons do not prove them.

Process names and creation timestamps do not attest executables or service
configuration. Same-PID execution changes, short-lived processes between
snapshots, I/O contention and memory-bandwidth contention are not ruled out.
Ordinary service restarts or changing kernel-worker names can require review;
do not weaken the policy after a timing outcome to retain that result.

## Validation

85 focused policy, existing observer and executor tests pass. They cover
zero-CPU unknown processes, PID reuse, name changes, migration, similar cgroup
prefixes, process births/deaths, permission failures, counter regressions,
observer placement, malformed timestamps/identities and policy errors.

The [negative replay receipt](threadripper_process_policy_negative_replay_20260928.json)
binds the two retained whole-host snapshots from each completed native fixture
to its original readiness, initial counter and host-summary records. All
12 input records and both source records were rehashed after reading. Each
replayed CPU diagnostic exactly matches the original interval.

| Retained fixture | Unreviewed snapshot entries | Distinct unreviewed PIDs | Changed identity/name/membership records | Observed foreign cores |
| --- | ---: | ---: | ---: | ---: |
| 22367, high sensitivity | 3,908 | 1,960 | 47 | 71.3577 |
| 22368, satellite_v2 | 3,919 | 1,962 | 57 | 74.5699 |
| 22369, full OrthoFinder | 3,917 | 1,962 | 50 | 74.6587 |

The replay intentionally uses an empty approved-process list. These counts
include ordinary processes and kernel workers; they are not counts of
scientific analyses. All three results are unresolved, as required. This is
a negative integration check on historical observations, not a newly approved
policy, live preflight, sensitivity estimate or fresh host-load measurement.

## Remaining Integration

Before this can support native release, the worker must bind a reviewed
service/executable configuration inventory and policy, verify the actual
scheduler job scope and observer readiness, collect fresh observations within
the handoff deadline, and retain its decision evidence. Whole-run review must
use the same prospective policy and retain failures without automatic retries.
Full-scale observer/resource validation, final executor recipe freeze and a
verified quiet window remain required by the
[executor contract](THREADRIPPER_EXECUTOR_CONTRACT_20260928.md). No preflight
or production execution permit was generated by this work.
